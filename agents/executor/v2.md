# Executor 2 on this Mac (cloud first)

As of 26 Oct 2026 the five agents on the Mac and on the julds VM use Executor 2. Executor 1
(`executor`, `executor_cloud`) is no longer configured in them. The VM reaches both through
stdio wrappers with bearer tokens (see `docs/boat-t3-workspace.md`).

| Agent entry | Endpoint | Holds |
|---|---|---|
| `executor_v2` | `https://executor-v2.julds.com/mcp?elicitation_mode=browser` (self-hosted on Cloudflare, fork `julds-ltd/executor-v2`, see its `JULDS.md`) | Everything that can run in the cloud: Notion, Granola, PlanetScale, Postman, Mobbin, Cloudflare (+ Bindings, Builds, Observability, Docs), Figma, Google, PostHog, GitHub, Exa, Context7, OpenAI Docs, Parallel |
| `executor_v2_local` | `http://127.0.0.1:4312/mcp?elicitation_mode=browser` (Mac only) | Only what needs this Mac: Paper, Playwright, 1Password, Aside, Agentation, shadcn, agent-desktop, Canva |

Rule: if a service can run in the cloud, it goes in `executor_v2`. Canva is local because
Canva's OAuth only allows its own callback list, which accepts `127.0.0.1` but not
`executor-v2.julds.com`.

## Client setup

```sh
uv run --script scripts/setup_executor_v2.py --check
uv run --script scripts/setup_executor_v2.py --retire-v1   # also removes the v1 entries
```

All five agents connect natively over streamable HTTP and sign in with OAuth on first use:

| Agent | Sign in |
|---|---|
| Claude Code | `/mcp`, pick the entry, Authenticate |
| Grok | `/mcp` in the TUI (headless `grok -p` does not start sign-in) |
| Codex | `codex mcp login executor_v2` and `codex mcp login executor_v2_local` |
| Cursor | `cursor-agent mcp login <name>` (entries present, not signed in yet) |
| OpenCode | `opencode mcp auth <name>` (entries present, not signed in yet) |

An Executor 2 OAuth credential is bound to the exact MCP URL it was issued for, including
`elicitation_mode` (no parameter means `model` mode). A credential used at another URL gets 403
`GrantForbidden` ("This credential works only at the MCP URL ending in /mcp..."). The five agents
were signed in at `?elicitation_mode=browser` and work there (re-checked 31 Oct 2026 with Claude,
Codex and Grok); keep the URL and the sign-in in step.

Aside (Settings > Plugins & MCPs > MCPs, streamable HTTP, OAuth "Auto", callback
`127.0.0.1:21420`) is connected to both, at the bare URL, because its grant is issued for `/mcp`
and the `?elicitation_mode=browser` URL then returns the 403 above:

| Aside name | URL |
|---|---|
| Executor-local | `http://127.0.0.1:4312/mcp` |
| Executor-cloud | `https://executor-v2.julds.com/mcp` |

Each lists 6 tools (skills, search, describe, call, execute, resume). At the bare URL Executor runs
in `model` mode: an approval comes back to Aside's model, which must ask in chat and answer with
`resume`; it does not open the browser approval page. Executor does not let a grant switch to
browser approval after it is issued. Treat Aside's approvals as client-side.

Do not use mcp-remote 0.13.5 for Executor 2: Executor returns the RFC 9207 `iss` parameter,
mcp-remote drops it, and its SDK then fails with `IssuerMismatchError`.

The templates carry the same entries: `agents/shared/mcp.json` (inventory),
`agents/opencode/opencode.jsonc` (both), `agents/opencode/opencode.cloud.jsonc` and
`agents/codex/config.toml` (cloud only, since the local endpoint exists only on the Mac).
`sync_agent_config.py` treats `executor_v2_local` like `executor`, so Codex direct defaults
are not re-seeded.

Executor 1 on the Mac is retired: its LaunchAgent `sh.executor.daemon` (port 4789) was unloaded
and its plist moved to `~/.config/executor-v2-local/retired-v1/`; its data in `~/.executor` is
kept. To bring it back, move the plist to `~/Library/LaunchAgents/` and
`launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/sh.executor.daemon.plist`.

Rollback: the pre-change configs are in
`~/.config/executor-v2-local/v1-agent-config-backup-*`; or rerun `setup_executor.py` to
re-add the v1 entries.

## Local Executor 2 and the stdio bridge

Executor 2 cannot launch processes, so stdio MCP servers sit behind
`scripts/executor_stdio_bridge.mjs`:

- Listens on `127.0.0.1:8930` only. URL: `http://127.0.0.1:8930/<secret>/<server>/mcp`.
  Wrong secret gives 404; any request with an `Origin` header gives 403.
- One long-lived stdio process per server, restarted on the next call if it exits.
- Config `~/.config/executor-v2-local/bridge.json` (0600), secret `bridge.secret` (0600).
  Servers: playwright (npx `@playwright/mcp@latest`), 1password (`/usr/local/bin/1password-mcp`),
  aside (`aside mcp`), agentation, shadcn (`scripts/executor_shadcn.mjs`), agent-desktop
  (`scripts/executor_agent_desktop.mjs`, see below).
- Node is the fnm `default` alias, which survives Node upgrades.

LaunchAgents (KeepAlive), loaded by `~/.local/bin/executor-v2-local-setup` (run in Terminal;
the Aside sandbox cannot bootstrap LaunchAgents):

| Label | Runs | Log |
|---|---|---|
| `com.julds.executor-v2-local` | `~/.local/share/executor-v2-lab/ev2 serve` (port 4312) | `~/Library/Logs/executor-v2-local.log` |
| `com.julds.executor-stdio-bridge` | the bridge (port 8930) | `~/Library/Logs/executor-stdio-bridge.log` |

Restart: `launchctl kickstart -k gui/$(id -u)/<label>`. Plist sources live in
`~/.config/executor-v2-local/`.

Approvals in local v2: 1Password asks on every call; agent-desktop asks for every tool not marked
read-only; the others ask only for tools the server marks destructive.

## agent-desktop (added 31 Oct 2026)

[agent-desktop](https://github.com/vercel-labs/agent-desktop) (Vercel Labs, Apache-2.0) does
desktop computer use through the macOS accessibility tree. It is a CLI with no MCP mode, so
`scripts/executor_agent_desktop.mjs` wraps it as a stdio MCP server for the bridge.

- Install: `agent-desktop@1.0.2` pinned in `~/.local/share/executor-local-tools`, with
  `"allowScripts": {"agent-desktop@1.0.2": true}` in its `package.json` (the postinstall links the
  bundled, checksummed native binary). Executor only: the binary is deliberately not on PATH
  (no `~/.local/bin` link), so agents cannot run the CLI and skip approvals. Check it with
  `tools["agent-desktop"].status`.
- Bridge entry `agent-desktop`: Node (fnm `default`) runs the adapter with the modules dir, the
  binary, and `~/.local/share/executor-local-tools/bin/disclaim-exec`.
- Local app `agent-desktop` (`app_e94212a2-…`), source in `~/.config/executor-v2-local/apps/agent-desktop/`
  (holds the bridge secret, 0600). Approval: every tool asks unless the adapter marks it
  `readOnlyHint` (snapshot, find, get, is, screenshot, list_apps, list_windows, list_surfaces,
  list_displays, wait, status). Acts (click, type, set_value, press, scroll, launch, run, ...) ask.
- Headless only: `--headed` and raw mouse/keyboard commands are refused unless a `run` call sets
  `allowPhysicalInput`. `--screenshot`, `--debug`, `--trace`, `--verbose` are always refused, and
  agent-desktop's stderr goes into the tool result, never into the bridge log. Snapshot refs are
  kept in `~/.agent-desktop` (0700).
- Not on the cloud executor or the julds VM: it needs this Mac's GUI.
- Skill: `agents/skills/agent-desktop` (routes agents to these tools, not to the CLI).
- Verified 31 Oct 2026 after the grant: Claude, Codex and Grok through `executor_v2_local` ran
  `list_apps` (87-91 apps, Finder listed) and `snapshot {app: "Finder", interactiveOnly, compact}`
  (178 refs) with no approval prompt; `run` returned `approval-required`. Finder needs an open
  window (`WINDOW_NOT_FOUND` otherwise). A full snapshot result can be too big for Codex to read;
  filter it in `execute`.
- Reminders (Automation permission is held only by Raycast): the accessibility tree still shows
  what is on screen without Automation. A read-only snapshot returned the sidebar list names
  and counts and the visible rows of the main pane. It is partial: subtrees come back
  `subtree_truncated`, the sidebar drill and `find` return `TIMEOUT` ("incomplete evidence",
  native read failures), and only what the window shows is visible. It is not a substitute for
  the Reminders data (EventKit/Automation).

### Accessibility and Screen Recording

The bridge is a launchd job, so macOS holds the bridge's Node binary responsible for every
process it starts, and a grant would have to go to Node (and with it to Playwright, Agentation
and every other bridged server). `scripts/disclaim_exec.c` (built to
`~/.local/share/executor-local-tools/bin/disclaim-exec`) starts agent-desktop with responsibility
disclaimed, so the grant belongs to the agent-desktop binary only. Grant, in System Settings >
Privacy & Security:

- Accessibility (named Device Control and Data Access on macOS 27): add
  `~/.local/share/executor-local-tools/node_modules/agent-desktop/bin/agent-desktop`
  (Cmd+Shift+G in the file picker) and turn it on.
- Screen Recording: the same file, only for `screenshot`.

The binary is ad-hoc signed, so the grant is tied to this build: after upgrading the pin,
remove and re-add it. agent-desktop keeps background host processes behind sockets in
`$TMPDIR/agent-desktop-host-<uid>/`, and a host keeps the grant of whatever started it, so the
adapter gives bridge calls a private `TMPDIR` (`~/.agent-desktop/bridge-tmp`, 0700) and never
reuses a host started from a terminal. Check from the bridge, not from a terminal:
`tools["agent-desktop"].status` through `executor_v2_local`.

Build the launcher on a new Mac:
`xcrun clang -O2 -Wall -o ~/.local/share/executor-local-tools/bin/disclaim-exec scripts/disclaim_exec.c`.

## Approval rules changed in the cloud

- Exa: `search` and `answer` run without approval (reads; they only cost Exa credits).
- PostHog: `exec` runs without approval for `search`, `info`, `help`, `list` and
  `call <tool>` where the tool name contains get/list/retrieve/search/query/read. Anything
  else asks. An approval policy takes one context object, `({ toolName, toolInput, signal })`,
  and for account-routed apps the command sits at `toolInput.input.command`.

Codex note: `codex exec -s read-only` blocks every Executor call ("requires approval, but
approval policy is never"), because `execute` is not marked read-only. Normal runs use
`danger-full-access` and work.
